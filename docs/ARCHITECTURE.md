# Архитектура ПрофПЛМ

## 1. Исследование предметной области и принятые решения

Исходный прототип (`Состав изделия.html`) решал одну задачу: загрузить спецификацию из Excel,
показать дерево и отмечать «пришло / можно собирать». Из него взяты и сохранены:
нормализация кодов, авто-поиск шапки по слову «Код», раскраска узлов по готовности снизу вверх,
сворачивание/разворачивание, добавление узлов. Всё остальное спроектировано заново с учётом
практики ГОСТ 2.503 (извещения), ГОСТ 2.106 (спецификации), MRP II и типовых процессов
машиностроительного завода (ПДО, ОГТ, ОТК, ОМТС, ОПК, цеха, бухгалтерия).

Ключевые решения:

| Вопрос | Решение | Почему |
|---|---|---|
| Как хранить историю состава | Состав принадлежит **ревизии** изделия, а не самому изделию | Любое извещение порождает новую ревизию; старые комплекты продолжают ссылаться на свою ревизию — история не теряется |
| Как «заморозить» состав конкретного заказа | **Комплект (Kit)** копирует развёрнутый состав в `kit_lines` с материализованным путём | Правка состава после запуска не ломает комплектацию; выборка поддерева — по префиксу пути, без рекурсии |
| Склад на больших объёмах | Движения append-only + **материализованные остатки** `(item, warehouse)` | Остаток читается за O(1); движения — источник правды для аудита и восстановления |
| Деньги | Проводки генерируются **автоматически** из движений | Бухгалтерия получает Дт/Кт без ручного ввода; экспорт в 1С одной кнопкой |
| Разные типы изделий | Один справочник `items` с `item_type` + `outsource_kind` | MRP выбирает действие (сделать / купить / кооперация) по типу; при этом состав, применяемость, цены общие для всех |
| ИИ и конфиденциальность | Трёхуровневая маршрутизация + human-in-the-loop | Конфиденциальные данные (уровень ≥ 2) никогда не уходят в облако; все изменения из чата требуют подтверждения |
| Доступ | RBAC по правам `domain:action` + допуск (clearance) к данным | Десятки ролей настраиваются администратором без правки кода; допуск отсекает конфиденциальные изделия даже при наличии права |

## 1a. Два слоя интерфейса

После первых отзывов («много разделов, непонятные слова, мелко») интерфейс перестроен вокруг работы плановика:

* **Простой слой** (`/api/simple/*`, экраны Заказы / Спецификации / Дефицит) — словарь пользователя: *спецификация*,
  *заказ*, *пришло*, *не хватает*. Отметки в заказе — чек-лист (`kit_lines.issued_qty/done`) и **не** двигают склад.
  Редактирование спецификации идёт в черновую редакцию, кнопка «Применить» выпускает её (с обходом вложенных узлов),
  «Отменить» удаляет черновики. Импорт Excel в один шаг с автораспознаванием колонок и вложенности по отступам.
* **Слой специалиста** («Ещё») — прежние экраны: складской учёт с проводками, закупки и ОТК, план/MRP, извещения
  с согласованием, аналитика, администрирование. Те же таблицы БД, так что данные плановика и бухгалтера не расходятся.

## 1b. Сборка: реальная и виртуальная

* Последовательность шагов — обход дерева заказа «снизу вверх» (`assembly._ordered_steps`): составляющие узла в порядке
  позиций, затем сам узел. Один список для цеха и для 3D.
* Факт: `kit_lines.done / skipped / done_at / done_by_id`; закрытие всех шагов переводит заказ в «укомплектован».
* 3D: таблица `item_models`, файлы GLB на диске (`PLM_MODELS_DIR`, volume `models`). STEP конвертируется через
  `cascadio` (OpenCASCADE), STL/OBJ — через `trimesh`. Сопоставление деталей с шагами — по нормализованному обозначению
  в имени узла glTF (на клиенте, three.js); разнесение по направлению от центра сборки, прогресс 0…N шагов.
* Закреплённое окно — Document Picture-in-Picture API; React-портал в документ PiP-окна с копированием стилей;
  обработчик клавиш навешивается и на основное, и на PiP-окно.

## 2. Технологический стек

* **Backend**: Python 3.11+, FastAPI, SQLAlchemy 2 (типизированные модели), Pydantic 2, PyJWT, bcrypt, openpyxl.
  Один процесс раздаёт API и собранный SPA; в проде — 4 воркера uvicorn за nginx.
* **БД**: PostgreSQL 16 (прод), SQLite (разработка/тесты). Схема управляется миграциями Alembic
  (`backend/alembic/`), применяются автоматически при старте; `render_as_batch` даёт совместимость ALTER с SQLite.
* **Frontend**: React 19 + TypeScript + Vite, без тяжёлых UI-библиотек (собственный набор примитивов ~200 строк CSS),
  тёмная тема по системной настройке, адаптив до 420 px.
* **ИИ**: локально — любой OpenAI-совместимый сервер (Ollama, vLLM, LM Studio), по умолчанию `qwen2.5:14b-instruct`
  (хорошо понимает русский и function calling); облако — Anthropic Claude (`claude-opus-5-5`) через официальный SDK.
* **Развёртывание**: docker compose (db, app, ollama, nginx, backup), TLS от корпоративного CA, rate-limit на `/api/auth/login`.

## 3. Модель данных

```
users ─┬─ user_roles ─ roles(permissions JSON)
       └─ audit_log

items (code, item_type, outsource_kind, confidentiality, lead_time, min_stock, lot_size, std_cost, external_ids JSON, attrs JSON)
 ├─ item_revisions (rev, status, change_notice_id) ── bom_lines (child_item_id, qty, position)
 ├─ operations (seq, work_center, setup/run hours, outsourced, outsource_cost, tooling_item_id)
 └─ default_supplier → partners

change_notices (number, reason_code, status, wip_disposition) ── change_lines (target, action, child, new_child, qty)
                                                              └─ approvals (role_code, user, decision)

plan_lines → kits (item, revision, qty, due) ── kit_lines (path, level, required/issued, done)
          └→ work_orders (item, qty, kit, status, actual_hours)

partners ── purchase_orders (kind: purchase|outsource, status) ── po_lines (qty, received_qty, price, due)
                                                                 └─ inspections (qty, accepted, rejected, status, lot, certificate)

warehouses ── stock_balances (item, wh, qty, reserved, avg_cost)
stock_moves (type, item, qty, from, to, unit_cost, lot, doc_ref, kit, work_order, user) ── journal_entries (Дт, Кт, сумма, exported)

connectors (kind, config JSON)      ai_messages (conversation, role, route, meta)
```

Индексы: по кодам/именам номенклатуры, по `(item_id, ts)` движений, по статусам документов, по `child_item_id`
(применяемость), по `kit_id` и `path`. На PostgreSQL для миллионов строк движений рекомендуется партиционирование
`stock_moves` по месяцам и `BRIN`-индекс по `ts`.

## 4. Процессы

1. **Изменение КД**: конструктор создаёт извещение (строки: добавить / исключить / изменить кол-во / заменить) →
   отправляет на согласование → каждый согласующий (по роли) ставит подпись → «провести»: для каждого затронутого
   изделия создаётся новая ревизия из текущей выпущенной с применёнными изменениями, выпускается, старая помечается
   устаревшей. Цепочка видна во вкладке «Ревизии» со ссылкой на извещение.
2. **Планирование**: ПДО ведёт товарный план → «Запустить» создаёт комплект (замороженный развёрнутый состав) и наряд
   на сборку → MRP разворачивает все невыполненные строки плана, вычитает доступные остатки (без карантина), открытые
   заказы и наряды, добавляет min-запас, округляет до партии и считает дату запуска назад от срока по циклам → ОМТС/ОПК
   одной кнопкой формирует заказы, сгруппированные по основному поставщику.
3. **Снабжение и качество**: приёмка по строке заказа → партия попадает в карантин как `inspection(pending)` →
   ОТК принимает/бракует → годные приходуются на основной склад (проводка Дт10/10.2 Кт60), брак — на склад карантина
   для рекламации. Остатки карантина не считаются доступными ни в дереве, ни в MRP.
4. **Производство**: мастер выдаёт детали в комплект (Дт20 Кт10), отмечает собранные узлы; закрытие наряда
   приходует готовое изделие по расчётной себестоимости (Дт43 Кт20).

## 5. Безопасность и доступ

* Пароли — bcrypt(12); блокировка на 15 мин после 5 неудачных входов; смена пароля/отключение пользователя
  инвалидирует все токены (поле `token_version` в JWT).
* Access-токен 8 ч, refresh 14 дней; фронтенд обновляет прозрачно.
* 26 прав вида `domain:action` (список в `security.PERMISSIONS`), 13 системных ролей (admin, конструктор, гл. конструктор,
  технолог, ПДО, инженер производства, мастер, ОТК, ОМТС, ОПК, кладовщик, бухгалтер, руководство). Роли редактируются в UI.
* Допуск 0–3 против `items.confidentiality`: без допуска изделие не видно в списках, не открывается и не уходит в облачный ИИ.
* Журнал аудита: каждое изменяющее действие (кто, что, когда, детали, источник ui/ai/import/integration).
* Заголовки `X-Frame-Options: DENY`, `nosniff`, HSTS на nginx; CORS ограничен доменом.
* Секреты интеграций хранятся только в переменных окружения; конфиг коннектора ссылается на них по имени (`password_env`).

## 6. ИИ-ассистент

```
запрос → [правила: состав / куда входит / себестоимость / дефицит / MRP / найди]   ← всегда, без LLM
       → [локальная LLM с инструментами]        ← если включена (конфиденциальные данные остаются в сети)
       → [облачная LLM с теми же инструментами] ← только если пользователь поставил галочку «облако»,
                                                   у него есть право ai:cloud и включено администратором
```

Инструменты (одинаковые для обеих моделей): `search_items`, `get_bom`, `where_used`, `get_cost`, `shortage_report`,
`run_mrp` — выполняются сразу; `propose_create_item`, `propose_bom_change`, `propose_stock_move` — возвращают
«предложение», которое пользователь подтверждает в чате (права проверяются как для обычного действия UI).
Если облачный ответ затронул данные уровня ≥ 2, маршрут помечается `cloud!` и фиксируется в аудите.
Расширение: загрузка файлов в чат использует тот же модуль Excel-импорта (`excel_import.preview/apply`).

## 7. Аналитика

* Дашборд KPI (дефицит, просрочки, очередь ОТК, брак, стоимость запасов).
* Прогноз расхода: сглаживание Хольта по недельным выдачам, страховой запас `1.65·σ·√L`, точка заказа, недели покрытия.
* Риски снабжения: скоринг (ниже min-запаса, долгий цикл, нет заказов, нет поставщика).
* Надёжность контрагентов: доля в срок, средняя задержка, доля брака → индекс.
* Загрузка рабочих центров по открытым нарядам против мощности.
Следующий шаг: ML-модели на истории (прогноз срыва сроков поставщиком, кластеризация дефектов) — данные для них уже накапливаются.

## 8. Масштабирование

* Статeless-API, горизонтальное масштабирование воркеров; PostgreSQL с пулом 20+40.
* Деревья: материализованные пути в комплектах, ограничение глубины, подсчёт остатков одним запросом на всё дерево.
* Импорт больших Excel — потоковое чтение (`read_only`); файл > 30 МБ отклоняется, рекомендуется разбивать по изделиям.
* Для >100 одновременных пользователей: вынести `_uploads` импорта в Redis, добавить фоновые задачи (MRP, синхронизация 1С)
  через RQ/Celery, кэш дашборда на 30 с.
